Грабли по порядку:
1. **Драйвер fastboot.** В fastboot телефон виден как `USB\VID_18D1&PID_D00D`, а официального Google USB Driver r13
   этот PID нет в `android_winusb.inf`. Ставили вручную: Диспетчер устройств → Обновить драйвер → Установить с диска →
   Android Bootloader Interface. Заодно выяснили, что в поле «Искать драйверы в следующем месте» путь вставлять бесполезно.
2. **Кнопки не пускали в fastboot.** Громкость+ + Громкость− + Питание держали по 30–60 с — телефон грузился как обычно.
   Обошли через `adb reboot bootloader`: после разблокировки в свежем OxygenOS отладка по USB уже включена,
   осталось разрешить доступ ПК (первое разрешение почему-то не сработало, помог повтор).
3. **Git Bash подменяет пути.** `adb push boot.img /sdcard/Download/` молча ушёл «в никуда»: MSYS превратил
   `/sdcard/...` в `C:/Program Files/Git/sdcard/...`. Для команд adb с путями на телефоне — `MSYS_NO_PATHCONV=1`.
4. **Play Protect** на Android 16 отклонил установку ADBKeyBoard по USB (`INSTALL_FAILED_VERIFICATION_FAILURE`).
   Повторили, пока владелец смотрел на экран, — прошло. Magisk ставился без вопросов.
5. **KernelSU-Next не подходит:** ядро 5.4 (`5.4.302-qgki`), а ему нужен GKI 5.10+. Root — Magisk, патч `boot.img`.
6. Модель теперь называет себя `LE2110`: единая сборка LineageOS для всех вариантов OnePlus 9. Это нормально.

## 2026-10-01 — день: этап 3, агент переезжает в телефон

- **Termux** v0.118.3 (официальный GitHub, SHA256 сверен) поставили через `adb install`. В нём Python 3.14.6 и Pillow 12.3.0
  из официального репозитория Termux. На телефоне ничего не набирали: `scripts/termux.py` выполняет команды внутри
  Termux с ПК — через root, от имени пользователя Termux и с его окружением.
- **Без тяжёлых зависимостей.** Пакет `openai` тянет `pydantic-core`, который в Termux пришлось бы собирать из исходников.
  Мозг переписан на `urllib` (с повторами при 429/5xx и сетевых сбоях), `.env` читаем сами. Из зависимостей остался только Pillow.
- **Telegram-бот** (`interfaces/telegram_bot.py`) — тоже на стандартной библиотеке: long polling, одно сообщение
  с прогрессом, которое обновляется на каждом шаге, итоговый скриншот, кнопки «Разрешить / Запретить» для опасных
  действий, `/stop`, `/shot`, `/status`. Слушается только владельца — это покрыто тестом, как и то, что чужой не может
  нажать «Разрешить».
- **Доставка:** `scripts/deploy.py` упаковывает код и `.env`, заливает в `~/LemonadeAgent` внутри Termux,
  (пере)запускает бота и может включить автозапуск через Magisk `service.d`.

Грабли:
1. **Без группы `inet` у процесса нет сети, даже DNS.** Приложениям Android доступ в интернет даёт группа 3003;
   `su <uid>` её не выдаёт. Лечится `su -g <uid> -G 3003 -G 9997 <uid>`.
2. **`su` в Termux.** На Android 16 Magisk кладёт его в `/debug_ramdisk/su`, а не в `/system/bin`. У Termux есть своя
   обёртка `su`, которая его находит, — `RootDevice` берёт её через `shutil.which`.
3. **`uiautomator` молча падал внутри Termux** (код 0, ни вывода, ни файла, ни строчки в logcat). Причина — в окружении
   Termux нет `BOOTCLASSPATH`, `ANDROID_ROOT` и т.п., а это Java-утилита. У `init` этих переменных на Android 16 уже нет —
   `RootDevice` берёт их из `/proc/<zygote64>/environ`. По дороге ещё и словили «could not get idle state»: дерево UI
   нельзя снять, пока на экране что-то анимируется (тут — всплывашка Magisk). Теперь это не ошибка, а откат на скриншот.
4. **Ложная тревога безопасности:** «Удалить запрос» (очистка строки поиска) совпала с правилом «удал…».
   Агент не получил разрешения и пошёл в обход — 12 шагов вместо ~5. Добавили исключения для поиска и очистки текста.
5. **Telegram API недоступен с телефона:** у провайдера заблокирован, а ПК ходит через AmneziaVPN. DeepSeek при этом
   доступен — поэтому сам агент работал. Нужен VPN и на телефоне.

**Первый запуск целиком на телефоне:** «включи светлую тему» → ✔ `Night mode: no`, 12 шагов, 85 с.
Скриншот изнутри снимается за 0,45 с против 2,3 с по USB, дерево UI — те же ~2,3 с (это ожидание «покоя» экрана).

### Эксперимент 1: память-подсказки не помогли

| | Раунд 1 | Раунд 2 | Раунд 3 |
|---|---|---|---|
| С памятью: успех / шагов / время / стоимость | 97% / 8,4 / 62 с / $0,115 | 93% / 8,0 / 58 с / $0,102 | 90% / 7,4 / 47 с / $0,069 |
| Без памяти | 93% / 8,0 / 58 с / $0,104 | 93% / 7,7 / 49 с / $0,071 | 93% / 7,7 / 62 с / $0,078 |

На первый взгляд — кривая обучения: шаги, время и стоимость падают. Но контроль без памяти тоже подешевел, а в раундах
2–3 (когда опыт уже есть) разницы нет: **7,7 шага против 7,7, $0,171 против $0,150 — с памятью даже дороже** (подсказка
удлиняет промпт), успех 55/60 против 56/60. Разбор по задачам показал, почему:

1. **Два «провала» — баги бенчмарка, а не агента.** На Android 16 у настроек «теневые» ключи: переключатель вибрации
   при касании живёт в `haptic_feedback_intensity`, а ползунок шрифта читает и `device_font_scale`. Бенчмарк готовил
   старт не через те ключи — интерфейс показывал «уже выключено», агент честно отвечал «уже сделано», проверка — «провал».
2. **Браузер с памятью стал хуже (10 → 19 → 20 шагов и провал), но память тут ни при чём — баг инструмента.**
   Нажатие на адресную строку ставит курсор в середину адреса, и `input text` вставлял текст туда: «goexample.comogle.com».
   Без памяти агенту просто чаще везло с курсором. А память добавила своё: в навык записался **грязный путь** первой
   удачной попытки (повторные вводы, нажатия «в точку») — и подсказка вела обратно в ту же яму.
3. Большинство задач и так короткие (3–8 шагов): подсказке почти нечего сэкономить, а модель всё равно думает на каждом шаге.

Что исправили:
- `type` теперь **заменяет** содержимое поля (Ctrl+A → Delete → ввод), дописать — `"append": true`;
- проверки шрифта и вибрации — через правильные ключи;
- навыки сохраняются «чистыми»: без нажатий в координаты и без повторных вводов подряд;
- **память v2 — повтор навыка**: если ровно эта задача уже решалась, агент проходит знакомый путь сам, находя кнопки
  по подписи, без модели. Последний, решающий шаг оставляем модели: состояние могло быть другим (слепой повтор «Включи
  Bluetooth» при уже включённом выключил бы его). Новая метрика — **вызовов модели на задачу**.

Проверочный прогон исправлений: вибрация, браузер (5 шагов вместо 20), крупный шрифт — проходят. «Верни стандартный
размер шрифта» по-прежнему проваливается — и это уже **честная ошибка агента**: у ползунка на Android 16 семь делений,
«стандартный» — второе, а агент рассуждает по-человечески «стандартный = посередине», ставит в центр и уверенно отчитывается.
Значение ползунка в дерево UI не попадает — только на картинке. Оставляем как трудную задачу.

Запущен эксперимент 2: «memory2» (подсказки + повтор) и «baseline2» — по 30 задач × 3 раунда.

Раунды 2–3: **5,3 вызова модели на задачу против 7,55 (−30%)**, $0,147 против $0,171 (−14%), успех 58/60 против 57/60.

- Повтор сработал в 51 из 60 задач раундов 2–3 — и все 51 успешны. В среднем повторялось 3,1 шага, модель вызывалась 4,7 раза.
- Самый большой выигрыш — на длинных задачах: «посчитай 3 + 4 и поставь будильник» — 2 вызова вместо 16 (47 с вместо 101 с),
  «создай контакт Android <версия>» — 2 вместо 11,5, «посчитай 1234 × 56» — 1,5 вместо 9.
- **Время не сократилось** (52 с против 51 с, 6,3 с на шаг против 6,8): узкое место — чтение экрана, `uiautomator dump`
  ждёт «покоя» ~2,3 с на каждом шаге, думает модель или нет. Следующая оптимизация — не модель, а восприятие.
- Где повтора не было: задача провалилась в раунде 1 (сохранять нечего) или путь начинался с жеста, записанного в
  координатах (открыть список приложений), — при чистке навыка он выкидывается, и повтор спотыкается на первом же шаге.
  Компромисс чистки; стоит научить навык сохранять жесты в переносимом виде.
- Провалы почти все — «верни стандартный размер шрифта» (в обоих вариантах), плюс два случайных разовых.
